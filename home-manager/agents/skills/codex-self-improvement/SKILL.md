# Codex Self Improvement

本業の問題を先に解決する。ユーザーが Codex の手順・品質を訂正した、または同種の失敗が反復したときだけ、改善案件を1件扱う。通常の質問、単発の仕様変更、根拠のない振り返りは対象外。明示呼び出しでは保留案件を1件選んで進める。1回1テーマで区切り、本業を無期限に止めない。

## 案件を残す

1. `~/.local/state/codex/self-improvement/` の既存 Markdown を関連語で検索し、同じ原因の案件があれば追記する。保存先がなければ `mkdir -p ~/.local/state/codex/self-improvement` で作り、新規案件は `uuidgen` の値をファイル名にする。ここは Git 外のランタイム状態であり、`~/.codex/memories` の代替知識集ではない。秘密値・生ログ・個人情報は保存せず、証拠の参照と最小限の匿名化した再現だけを残す。
2. 以下の項目を短く埋める。未知は「未確認」と書く。未検証案を規則や事実として扱わない。

```md
# <1テーマの名前>
- 状態: 保留 | 評価中 | 採用 | 棄却
- 期待 / 実際: <それぞれ1文>
- 証拠: <匿名化した事象と参照先。生ログ・秘密値は入れない>
- 改善対象 / 適用範囲: <管理元、実体、対象タスクと対象外>
- 再現ケース / 固定合格条件: <変更前に定める中央値・境界ケース、各判定条件>
- 変更前 / 変更後: <差分または案、同条件の結果。未計測は未計測と書く>
- 次アクション: <担当する1手と必要な確認>
```

## 進め方

1. 事象の原因と変更先を絞り、管理元と実体、参照元、既存の他者変更を確認する。KB は検証済み事実、Skill は再利用手順、hook・設定は機械的なチェック、AGENTS は短い起動導線に使う。権限拡大、自動投稿、`~/.codex/memories` の変更はしない。
2. 変更前に匿名化した再現ケースと固定合格条件を定める。対象の実作業から1件、別の関連ケースを1件用意する。元の依頼の権限内なら最小変更を検証して適用する。範囲外なら具体的な差分案と評価方法を案件に残し「保留」にする。
3. Skill・指示文を変える場合は `../empirical-prompt-tuning/SKILL.md` に従い、変更前後を同条件の新規実行者で比較する。fixture または一時 workspace で行い、外部投稿や実サービス変更はしない。未使用の別ケースでも確認する。新規実行者を使えない、参照 Skill がない場合は自己採点で代替せず「保留」にする。モデルやツールの計測値が得られなければ「計測不能」と記録する。機械的変更には対応するテストを行う。
4. 固定条件を満たした変更だけ「採用」とし、結果・根拠・次アクションを案件に残す。不合格は「棄却」、継続調査は「保留」。採用後に同じ失敗が再発したら案件を「評価中」に戻して再評価する。未検証の案を改善完了と報告しない。

次の関連タスクでは案件を検索し、適用範囲と現在の事実を確認してから採用済みの改善を使う。報告は案件の状態、根拠、次アクションを簡潔に述べる。
