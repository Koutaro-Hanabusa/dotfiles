## 軸は用途で使い分ける（混ぜない）

「軸」は文脈で3つあるので、**先にどれを聞かれているか確定**する。

| 用途 | どの軸 | 出典 |
|------|-------|------|
| 候補企業を**挙げる／落とす**（リストアップ・スクリーニング） | **リストアップ軸** | `home/knowledge/転職候補のリストアップ軸（スクリーニング条件）.md` |
| 面接で「なぜ転職？なぜ御社？」を語る、動機を整理する | **転職理由の4軸** | `home/knowledge/転職理由の4軸.md` |
| 特定企業の面接対策で自分の軸と接続する | 上記両方＋その企業別の対策ノート | `kb search "<企業名>" -n home` |

### リストアップ軸（候補企業スクリーニング・本人原文 2026-08-04）

1. **エンジニアが30人以上いてほしい**（技術投資の予算感の代理指標）
2. **FEに軸足をおける**（FE専門枠でなく、統合ポジションでもFEを主戦場にできる）
3. **エンタメに関係するプロダクト**
4. **カンファレンスの文化があるか**（社員登壇・参加費負担・スポンサー実績）

- 4条件すべて ⭕ → 実検証（採用ページを開く）へ進める
- 1つでも ❌ → 原則落とす。例外理由が明確なら「サブ候補」に置く
  （例: サイボウズは軸3❌だが他が強い → サブ）

### 転職理由の4軸（面接での語り・本人原文 2026-05-07）

1. **スピード感** — 意思決定が速く、アウトプットがユーザーに届く環境
2. **設計力の活用** — DS構築・0→1画面設計を、実フィードバックが回る場で発揮
3. **組織目標へのコミット** — 「組織の目標があって、それに対して私もコミットする」
4. **ドメインへの当事者性** — 「誰かの熱量を支える・生み出す」を「娯楽や、エンタメの面で」

- **非妥協は軸4のコア**＝「誰かの熱量を支える・生み出す」こと
- 「娯楽・エンタメで」は軸4のサブ。「必ずしもエンタメである必要はないが、優先したい」

### 軸を扱うときの禁則

- **本人原文を勝手に抽象化・キャッチコピー化しない。** 転職理由の軸3 はかつて AI が
  「ビジョン駆動」とラベル化し、本人の言葉ではないと指摘されて差し戻された。原文があるものは原文で扱う
- 転職理由の軸4が正面マッチしない企業は、上位抽象「誰かの何かをよくする」で接続してよい。
  ただし**軸4のコア定義そのものは書き換えない**
- **リストアップ軸と転職理由の4軸を混ぜない。** 「軸なに？」と聞かれたら、
  まずどっちのことか確認する

## 除外条件

- **VR / VTuber 系**: カバー(hololive) / ANYCOLOR(にじさんじ) / バルス(SPWN) / REALITY /
  ミリプロ / VOLVE CREATIVE
- 開発職の募集自体がない企業
- FEを軸足に置けない企業（BE専任・インフラ専任・SREのみ 等）

## 機能

### 1. 企業リサーチ (`research`)

**まず kb を引き、既出企業なら過去の判定を出発点にする。** ゼロから調べ直さない。

**収集項目**（=リストアップ軸を検証するのに必要なもの）:
- 企業名（日英）／主要プロダクト・サービス
- **エンジニア人数**（30人以上か・技術投資の予算感を測る）
- **FEを軸足に置ける役割があるか**（FE専門枠の有無ではない）
- **エンタメ関連プロダクトか**
- **カンファレンス文化**（社員登壇・参加費負担・スポンサー実績）
- 技術スタック
- 資金調達・上場状況
- 採用ページURL（**実ページを開いて確認した URL**）
- 年収帯（公開されている場合）

**出力**: 表形式。**リストアップ軸4条件それぞれに ⭕/△/❌ を付ける**。
1つでも ❌ なら原則落とし、例外理由が明確な場合のみ「サブ候補」に置く。
面接段階まで進む企業は転職理由の4軸との接続マップも別途作る（機能4 `prep`）。

### 2. 求人検索 (`search`)

**検索先**:
- **企業の公開採用ページ（必須・これが一次情報）**
- Green, Wantedly, Findy, HERP 等の求人媒体は**候補の当たりを付ける用途のみ**

> ⚠️ **媒体のインデックスと実ページは乖離する。** pixiv・Anique では媒体検索で「FE募集あり」と出るのに
> 実ページが 404 だった。**媒体の情報を根拠に応募判断してはいけない。**
> 公式採用ページの URL 自体も変わる（Gaudiy: recruit.gaudiy.com → special.gaudiy.com へ301、
> TwoGate: .co.jp ではなく .com）。

**収集項目**: ポジション名 / 必須・歓迎スキル / 年収帯 / 勤務形態（リモート可否）/ 応募URL /
**フロントを担当できる範囲**（統合ポジションの場合、FEがどこまで含まれるか）

### 3. 応募管理 (`track`)

候補リストのノートを直接更新する（`kb search` でパスを取り → Edit → `kb sync`）。
`kb edit` は存在しない。

**管理項目**: 企業名 / ポジション / ステータス（興味あり・応募準備中・応募済・書類通過・面接中・内定・見送り）/
応募日 / 次のアクション / メモ / **リストアップ軸4条件の判定**（応募段階で再確認）

### 4. 面接対策 (`prep`)

- **先に `kb search "<企業名>" -n home` を実行**。既に対策メモがあれば追記で育てる（新規作成しない）
- 企業の技術ブログ・テックスタック・登壇実績を調査
- 想定質問リスト（技術質問 + カルチャーフィット）
- **転職理由の4軸** × その企業の接続マップを作る（リストアップ軸ではなくこちら）。
  **ズレる軸は正直に扱う**（無理に整合させない。ズレの伝え方を用意する）
- ポートフォリオで強調すべきポイント

### 5. 市場分析 (`market`)

- 業界の最新ニュース・資金調達情報
- ポジションの形の変化（FE専門枠 → 統合ポジション のようなトレンド）
- 技術トレンド、給与相場

## 使い方

```
/job-hunter                    → メニュー表示
/job-hunter research {条件}     → 企業リサーチ
/job-hunter search {企業名}     → 求人検索

/job-hunter market             → 市場分析
```

## 実行ルール

1. 返答は必ず**日本語**で行う
2. **Web 検索の前に kb を引く**（`knowledges` スキルと併用。重複リサーチと過去判断の踏み外しを防ぐ）
3. **求人の現存は必ず公開採用ページを開いて確認する。** 媒体情報・検索インデックスは根拠にしない
4. 企業情報には**実際に開いた URL** を添える。開いていない URL を書かない
5. 「軸なに？」と聞かれたら**まずどの軸か確認**（リストアップ軸 / 転職理由の4軸）。混ぜない
6. **候補選定はリストアップ軸4条件で判定**（30人以上・FE軸足・エンタメ・カンファ文化）。
   1つでも ❌ なら原則落とす
7. **面接対策では転職理由の4軸で接続マップを作る。** 軸4のコアが欠ける企業は無理に整合させない
8. FE専門枠の有無ではなく「**FEを軸足に置けるか**」で判定する
9. 面接対策では企業の技術ブログ・登壇実績を必ず確認する
10. リサーチ結果は表形式でまとめる
11. **新しい発見・判定の更新は kb に書き戻す**（`kb new` / `kb sync`）。
    候補企業の適合判定が変わったら候補リストのノートを更新する
12. 求人情報には鮮度がある。**調査日を必ず書く**（4か月で大きく陳腐化した実績あり）
