このスキルはセッション全体を通じてナレッジベースへの自動記録を管理します。記録には自作の
`kb`（Rust 製ナレッジ CLI）を使います。`nb` は廃止済みです。

## 記録ルール

- **ノート作成は必ず `kb new -t "<タイトル>"` を使う。** `-t` は省略可能なオプションではありません
  （省いたときに何が起きるかは後述）。frontmatter の生成もノートブックの選択も kb が行うので、
  手書きする箇所はありません。
- ノートブックはマシンから自動判定される — `~/.is_work_pc` があれば `work`、なければ `home`。
  意図的に上書きする場合を除き `--notebook` は渡さないこと。
- 同期は `kb sync`。Markdown だけを stage し、生成したメッセージでコミットしてから pull・push する。
- 記録はバックグラウンドで実行すること（Bash で `run_in_background: true`）。会話フローをブロックしない。
- ユーザー確認は不要 — 常に自動で記録する。
- ハーネスがネットワークを塞いでいると `kb sync` の push が失敗することがある。その場合は
  `! kb sync` をユーザー自身に実行してもらう。

## 記録対象

- Q&Aのやりとり（質問とその回答）
- コードレビューの学び（例：バリデーションルール、フレームワークの挙動）
- デザインパターンの発見（例：アーキテクチャの意思決定、状態管理のアプローチ）
- バグ修正とその根本原因
- セッション中に得られたあらゆる知見

## 記録方法

### 1. 説明的なタイトルを決めて `-t` で渡す

`-t` は frontmatter の `title` とファイル名の両方になります。後からの検索性はここで決まります。

**タイトルを位置引数で渡しても効きません。** `kb new "<タイトル>" --content -` の位置引数は
*本文* として扱われます（拡張子付きのときだけファイル名と解釈される）。`-t` が無いと kb は本文の
1行目からタイトルを拾い、ファイル名は時刻（`20260729095853.md`）になり、`# 見出し` も書かれません。
work ノートブックには 2026年7月時点でこの形式のノートが26件あり、実質的に検索不能です。
このスキルが破られる原因はほぼこれ1つです。

良い例: `TanStack Router の routes を薄く保つ方針`、`OAuth PKCE flow の落とし穴`、
`postgres jsonb index のトレードオフ`

悪い例: `メモ`、`学び`、`tanstack`（広すぎ）、`20260429153423`（`-t` を忘れると生成される形式）

### 2. 1コマンドでノートを作る

```bash
kb new -t "<説明的なタイトル>" --folder knowledge --content - <<'EOF'
## <セクション1>

- 要点
- 必要に応じてコード例

## <セクション2>

...
EOF
```

本文のルール — 実際に守られていないのはここです:

- **`# H1` を書かない。** `kb new -t` が本文の先頭に `# <タイトル>` を自動で挿入します。
  手書きすると重複します。
- **`## Date:` の行を書かない。** frontmatter に `created` / `updated` が既にあり、手書きの日付は
  そこからズレていきます。日付を本文に書くのは*内容自体*が時点依存のとき（ある日時点のスナップショット、
  調査結果など）だけにし、その場合はセクション見出しに含めること。
- **`##` セクションを必ず2つ以上。** 1段落の散文はノートではなく、二度と見つけられない文章です。
  `## 事象` / `## 原因` / `## 対応`、`## 結論` / `## 根拠` のように、知見の形に合わせて割ること。
- コマンド・コード・ファイルパスはフェンスドブロックに入れる。検索とコピペに耐えます。

`--folder` が保存先です。タグは省略するとフォルダ名になるので、変えたいときだけ `--tags タグ1,タグ2` を渡します。

### 3. kb が実際に書いたものを確認する

`kb new` は書き込んだパスを表示します。次に進む前に必ず読むこと:

- ファイル名がタイトルになっているか。時刻だけの名前になっていたら `-t` が抜けています。
  `kb delete <パス>` で消してからやり直すこと。
- 既存ファイルを上書きすることはなく、タイトルが衝突した場合は `-2` が付きます。

### 4. 同期

```bash
kb sync
```

### 5. 既存ノートの更新

`kb edit` は存在しません。まず探して、Edit ツールで直接編集します:

```bash
kb search "<検索語>" -l    # マッチしたノートのパス
kb ls --since 7d          # 最近更新したノート
```

編集後に `kb sync` で反映します。

## ノートのフォーマット

frontmatter *と* `# <タイトル>` の見出しは `kb new -t` が書きます。渡すのはその下のセクションだけです:

```markdown
## <セクション1>

- 要点

## <セクション2>

...
```

生成されるファイル（自分では書いていない `# 見出し` が入る点に注意）:

```markdown
---
title: <渡したタイトル>
tags: [knowledge]
created: 2026-07-29T12:14:54+09:00
updated: 2026-07-29T12:14:54+09:00
---

# <渡したタイトル>

## <セクション1>

- 要点
```

## 重要事項

- **`-t` は必須。`nb` は廃止済み。** frontmatter を手書きしない。生の `git add`/`commit` も
  使わない — 無関係な stage 済みファイルをノートのコミットに巻き込まないために `kb sync` がある。
- **タイトル = 検索性。** 汎用的なタイトルやタイムスタンプは後から探せない。
- **セクション = 半年後の可読性。** 1段落の散文は書いた日には十分に見えて、後から役に立たない。
- 関連する学びは多数の小ファイルを作るのではなく、1つのノートにまとめる。
- 常にバックグラウンドで実行すること — ユーザーを記録処理で待たせない。
